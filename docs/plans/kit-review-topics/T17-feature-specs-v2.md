**Additions (2026-07-28, from the T33 grill — reviewer-consumer requirements + worked example):**
- **T17.9 — Self-containment doctrine (decision-worthy).** A feature spec is a **complete, separate, self-contained, environment-agnostic** document (or series). It **lists** feature-decisions with their reasoning and answers to specific questions, holds BRs / journeys / personas / descriptions / NFRs, and **refers to** existing ADRs and decisions — but it **never prescribes** ADRs, architecture, physical data models, or decision-log entries. Two independent reasons (Chris, 2026-07-28): (a) ADR/decision **numbering drifts** and parallel features (fosters, volunteer-tracking, SOC 2) move the architecture underneath the spec; (b) the spec author often **lacks the architectural context** to decide *how* — it's a **separation of roles**: the spec author states *what* with the context they have; the development-time **assessor**, who has architectural context, decides *how* (ADRs, physical model) when the spec is assessed for development. SPEC-ADOPT-000 §"Scope of this document" and §3 already model this ("these are not decision-log entries and not ADRs"; "requires an architecture decision at assessment").
- **T17.10 — The SPEC-ADOPT-000…006 set is T17's worked reference example** (adopter Companion): a 7-doc series with an overview holding cross-cutting content (scope, feature-decisions FD-n, NFRs, cross-cutting BRs, referenced existing decisions) and per-flow specs. Use it to shape the v2 template — and note what it does *well* (feature-decisions-with-reasoning, referenced-not-restated existing decisions, conservative-default BRs, per-flow ECs).
- **T17.11 — Reviewer-consumer requirements (from T33; form-only, compatible with self-containment).** T33's reviewers consume the spec, so the template should surface, as *declared/addressable* content rather than prose: (a) **feature-specific invariants** — the always-must-hold assertions (e.g. SPEC-ADOPT NFR-1 org-isolation, "no cross-org read under any parameterization") are today buried in an NFR paragraph; the reviewer needs them declared; (b) **UX/tone clauses** filed as such rather than as business rules (e.g. SPEC-ADOPT-005 BR-17/BR-18 "no language implying failure" are UX-conformance checks in BR clothing). **Not** in scope for the template: a physical conceptual→physical **binding** slot — that would violate T17.9's self-containment; the binding is a T33 review-time / development-assessment artifact, and an absent binding sends the verifier to `BLOCKED` (T33.12).
- **T17.12 — Notation freedom.** Specs should not be limited to a single Mermaid flowchart. Invite the **right** diagram per shape — a **state diagram** for lifecycles (adoption unclaimed→claimed→returned→re-intake), an **entity-relationship** view for tenancy shapes (adopter↔relationship↔shelter, FD-6), a **sequence** for multi-actor handoffs (QR/email/consent claim) — all native to Mermaid, plus non-diagram markdown (tables), and freedom to use another representation where markdown genuinely can't express it (relates to T35).
- **T17.13 — BR-authoring guidance (folded in from the T33 grill).** A good business rule states the **requirement**, not the implementation or procedure — though the requirement *may itself be* a specific procedure ("confirm twice before deletion"); either way the testable question is "can we do it the way specified?" Sharpen the template's current "stated testably" with this. (Relevant to T33.4: a procedurally-stated BR is still valid reviewer input — it's *what should be true*, not forbidden how-to.)
